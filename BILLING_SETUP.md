# Central Polar billing deployment

The implementation supports FrameDrop, WhatsApp Commerce, Qube Auth, and future plugins using verified shared Qubtic accounts. Plugin purchases are separate. This bills the Qubtic plugin license; it does not process a merchant's storefront orders.

## Before deployment

1. Back up the database. Apply `supabase/framer_users.sql` and `supabase/pairing_sessions.sql` only on a new database. Apply `supabase/free_pro_only.sql`, then `supabase/billing.sql`, then `supabase/billing_central_config.sql`. The billing migration also closes public access to shared auth/session records; the Qubtic server MUST have its service-role credential before deployment. `auth_server_only.sql` is available separately for auth-only deployments.
   Apply `supabase/billing_discounts.sql` before deploying discount-aware billing. It adds Polar-confirmed subtotal and discount fields to payment history and refreshes the plugin payment views. It is safe to reapply.
2. Set server variables from `.env.example`: Supabase service-role key, `POLAR_ENVIRONMENT`, `POLAR_ACCESS_TOKEN`, `POLAR_ORGANIZATION_ID`, `POLAR_WEBHOOK_SECRET`, `BILLING_CRON_SECRET`, SMTP credentials, and the admin signing secret. No provider secret belongs in a plugin or public environment variable. Use the minimum necessary Polar token scopes: product/customer/order/subscription reads, checkout writes, and customer-session creation. Pin and review the official SDK/API version (`@polar-sh/sdk/2026-10`).
3. In Polar sandbox create three fixed-price products per plugin: monthly recurring, yearly recurring, and lifetime one-time. Use one reserved Pro benefit per plugin attached to all three products. Do not reuse a plugin's benefit for unrelated products. Set no trial, no lifetime expiration, and immediate benefit revocation on failed subscription payment for this release. All three billing options give identical Pro features. Account-based activation is used; manual license-key redemption is intentionally unnecessary.
4. Copy the central product/benefit ENV groups from `.env.example` into the private server environment and fill them there, then run `npm run billing:check`, `npm run billing:configure`, and `npm run billing:check -- --remote`. Keep `.env.example` credential-free. Runtime checks that the active database catalog matches ENV. Never guess live IDs or copy sandbox IDs into production. Retain disabled old catalog rows so historical products remain recognizable. The partial unique index allows one enabled product per plugin/cadence.
5. Register `https://www.qubtic.tech/api/billing/webhook` in Polar. Subscribe to `customer.state_changed`, `customer.deleted`, order paid/updated/refunded events, subscription updates, benefit-grant updates/revocations, and refund events available for the pinned API version. Signature validation uses the original request body and official SDK. Unknown signed event types are acknowledged without granting access.
6. Schedule POST `/api/billing/reconcile` with `Authorization: Bearer <BILLING_CRON_SECRET>` every minute. Each call retries up to ten pending events and refreshes ten known customers plus up to ten pending checkout owners, oldest attempt first. External-ID discovery recovers a purchase even when its first webhook was missed. Increase frequency or batch capacity as the customer base grows; every paying customer must be reconciled inside the one-hour access lease. Use a scheduler supporting HTTP POST; do not assume a GET-only scheduler works. Monitor returned failures and event attempts. Events reaching 20 attempts require operator investigation and resetting attempts after the root cause is fixed.
7. Deploy Qubtic and all three rebuilt plugins together. Old browser activation flags and pasted authentication tokens cannot authorize new paid access. Production auth never revives rotated/revoked tokens from old pairing snapshots; plugin sign-out revokes the server token. Existing server `framer_users.plan` values no longer determine paid access: Polar-backed `plugin_entitlements` do. The return page never grants Pro.

For exact dashboard clicks, credentials, ENV names, and acceptance checks, follow [POLAR_DASHBOARD_GUIDE.md](POLAR_DASHBOARD_GUIDE.md).

## Behavior and operations

The plugin sends only a cadence and a request UUID. The authenticated server chooses the product and ties checkout to a verified billing identity. Independently verified memberships with the same normalized email share a customer; plugin permissions remain separate. Sandbox and production memberships are separated. Cross-account reassignment, unknown products, wrong billing intervals, and duplicated active checkouts are rejected.

Signed webhooks are stored durably before processing. Processing fetches current Polar customer state, complete order history, and subscriptions; an atomic database function writes history/access and rejects older snapshots. Re-deliveries are idempotent. A success URL or browser message never activates Pro. Renewing access requires the correct benefit plus a paid order for the current subscription period. Partial refunds retain access to the remaining purchase; full refunds remove that source. A separate valid lifetime purchase continues to grant access when a recurring subscription ends. Cancel-at-period-end retains access only through the paid period. This release does not offer payment-failure grace access.

An entitlement is verified for at most one hour and no later than a recurring paid period's end. Provider/database outages do not invent paid access; previously verified access expires at that bound. Billing stays unavailable until configured. Payments can be retried only through a new or still-valid checkout; uncertain failed creation is not automatically retried by application code.

The shared billing panel appears in the three plugins and at `/billing` on Qubtic. Purchase history shows up to 100 recent orders for the selected plugin; the Polar portal provides invoices and subscription management. Refresh runs after focus and every 15 seconds for up to two minutes after opening checkout. If a popup is blocked, a Continue to Polar link is shown. The return page is a neutral handoff, not a receipt.

Database views `frame_drop_plugin_payments`, `whatsapp_commerce_plugin_payments`, and `qube_auth_plugin_payments` expose per-plugin records to server/admin operators. All billing/auth tables and functions are server-only. A public view is not an authorization boundary. Server credentials must never be shared with customers. Keep proxy headers trustworthy, HTTPS enabled, and logs free of tokens and webhook secrets. Establish retention/backup policy for webhook payloads and payment records; payloads contain customer data.

## Acceptance before real payments

Run the local tests/builds, then use Polar sandbox for all three cadences and all plugins. Verify paid activation, delayed/duplicate/reordered webhooks, wrong-product/account requests, canceled checkout, scheduled cancellation, failed renewal, partial/full refunds, lifetime plus canceled recurring access, blocked popups, sign-out/account switching, and database/Polar outages. Confirm actual order history/invoices and cron monitoring. Local tests mock Polar network and SMTP; they do not certify live payment delivery or production readiness.

Payment cards stay on Polar. Local generated Framer components and bundled client code remain inspectable/copyable; a client-side paywall is not DRM. Sensitive paid backend services must independently authorize every request. No production purchase, deployment, remote database migration, or live email delivery is performed by this implementation task.
